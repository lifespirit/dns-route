# Описание параметров

[English version](configuration.md) · [К README](../README.rus.md)

## Модель конфигурации

`dns-route` хранит постоянную конфигурацию в SQLite. Web-панель изменяет базу транзакционно: новая runtime-конфигурация сначала собирается и активируется, и лишь после этого транзакция фиксируется. Если активация не удалась, изменения базы откатываются.

У демона всего два CLI-флага. Поведение DNS и маршрутизации настраивается в SQLite, обычно через web-панель.

## Параметры командной строки

| Флаг | По умолчанию | Назначение |
|---|---:|---|
| `-db` | `/var/lib/dns-route/config.db` | Путь к SQLite. База и отсутствующие таблицы создаются при запуске. |
| `-http` | `127.0.0.1:8080` | Адрес встроенного admin HTTP-сервера. |

Пример:

```bash
dns-route -db /var/lib/dns-route/config.db -http 127.0.0.1:8080
```

## Настройки

Параметры хранятся в таблице `settings(key, value)`. Истиной считаются `1`, `true`, `yes` и `on` без учёта регистра; остальные значения — ложь. Web-панель записывает boolean как `1` или `0`.

| Ключ | По умолчанию | Назначение |
|---|---:|---|
| `wg_interface` | пусто | Linux-интерфейс kernel backend. Историческое имя сохранено, но технически это может быть любой подходящий L3-интерфейс, не только WireGuard. |
| `wg_gateway_v4` | пусто | Обязательный IPv4 next hop для kernel-маршрутов из A-ответов. |
| `wg_gateway_v6` | пусто | Необязательный IPv6 next hop. Если пусто, IPv6-маршрут создаётся только через устройство. |
| `route_mode` | `kernel` | `kernel`, `bgp` или `kernel+bgp`. |
| `route_table` | `0` | Таблица маршрутизации Linux. `0` означает main table `254`. |
| `route_ipv4` | `true` | Создавать/анонсировать маршруты из A-ответов. |
| `route_ipv6` | `true` | Создавать/анонсировать маршруты из AAAA-ответов. |
| `local_record_ttl` | `60` | TTL локальных записей, у которых в базе `ttl=0`. Неотрицательное число. |
| `lookup_cidr` | `true` | Искать покрывающий префикс через DNS TXT Team Cymru. Имя оставлено для совместимости. |
| `reply_before_route` | `false` | Отвечать сразу и ставить маршрут асинхронно вместо ожидания установки. |
| `listener_freebind` | `false` | Использовать Linux `IP_FREEBIND`/`IPV6_FREEBIND` для ещё не существующих адресов listener'а. |
| `bgp_local_asn` | пусто | Локальный ASN, обязателен для BGP-режимов. |
| `bgp_router_id` | пусто | Ненулевой IPv4 router ID, обязателен для BGP. |
| `bgp_peer_address` | пусто | IPv4- или IPv6-адрес BGP-peer. |
| `bgp_peer_asn` | пусто | ASN peer'а. |
| `bgp_local_address` | пусто | Необязательный source address BGP TCP-соединения; семейство должно совпадать с peer. |
| `bgp_next_hop_v4` | пусто | Обязательный IPv4 next hop при включённой IPv4 BGP-маршрутизации. |
| `bgp_next_hop_v6` | пусто | Обязательный IPv6 next hop при включённой IPv6 BGP-маршрутизации. |
| `bgp_password` | пусто | Необязательный TCP MD5 password. Панель никогда не показывает сохранённое значение. |
| `bgp_multihop_ttl` | `1` | BGP multihop TTL от 1 до 255. Значение выше 1 включает eBGP multihop. |
| `bgp_require_established` | `false` | Считать BGP-маршруты готовыми только при состоянии peer `Established`. |

### Режимы маршрутизации

#### `kernel`

Маршруты добавляются в выбранную Linux-таблицу через `netlink.RouteReplace`.

- Для IPv4 обязательны `wg_interface` и `wg_gateway_v4`.
- Для IPv6 обязателен `wg_interface`; `wg_gateway_v6` можно оставить пустым.
- Уже существующий покрывающий маршрут в snapshot backend'а может подавить создание более специфичного маршрута.

Для split routing рекомендуется отдельная policy-routing таблица. В main table `254` обычно уже есть default route, который способен влиять на проверку покрытия.

#### `bgp`

Маршруты только анонсируются встроенным GoBGP и не создаются в Linux-таблице.

Desired-набор хранится в памяти процесса. После полного рестарта он заново собирается из последующих подходящих DNS-ответов.

#### `kernel+bgp`

Сначала точный префикс создаётся в выбранной Linux-таблице, после чего тот же префикс анонсируется через BGP. При запуске и ручном **Reload routes** выбранная kernel-таблица используется для восстановления desired-набора BGP.

Если новый набор удалось анонсировать не полностью, старые BGP-маршруты в рамках неудачного reconcile не отзываются.

## DNS-listener'ы

Адреса хранятся в `listen_addrs`:

```sql
CREATE TABLE listen_addrs (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  addr TEXT NOT NULL UNIQUE,
  enabled INTEGER NOT NULL DEFAULT 1
);
```

Примеры:

```text
127.0.0.1:53
192.168.1.1:53
[fd00::1]:53
```

Для каждого включённого адреса создаются одновременно UDP- и TCP-listener.

Если адрес нельзя привязать:

- при `listener_freebind=0` он остаётся pending и повторяется каждые три секунды;
- при `listener_freebind=1` демон просит Linux разрешить bind до появления адреса.

Изменение списка приводит к reconcile активных и pending listener'ов без рестарта процесса.

## Основные upstream

Основные DNS-серверы хранятся в `upstreams`:

```sql
CREATE TABLE upstreams (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  addr TEXT NOT NULL UNIQUE,
  proto TEXT NOT NULL DEFAULT 'auto',
  enabled INTEGER NOT NULL DEFAULT 1,
  priority INTEGER NOT NULL DEFAULT 100
);
```

Поддерживаемые протоколы:

| Значение | Транспорт |
|---|---|
| `auto` | Определяется по scheme или порту; порт 853 означает DoT, остальные адреса — UDP |
| `udp`, `dns` | Обычный DNS по UDP |
| `tcp` | Обычный DNS по TCP |
| `tls`, `dot` | DNS-over-TLS |
| `https`, `doh` | DNS-over-HTTPS POST с `application/dns-message` |

Примеры адресов:

```text
1.1.1.1
1.1.1.1:53
[2606:4700:4700::1111]:53
udp://1.1.1.1:53
tcp://192.0.2.53:53
tls://dns.example:853
https://dns.example/dns-query
```

Для DoT используйте hostname, если сертификат выдан на DNS-имя. IP literal становится TLS `ServerName` и требует сертификат, действительный для этого IP.

Обрезанный UDP-ответ автоматически повторяется по TCP.

### Приоритет и балансировка

Сначала пробуются меньшие числовые priority. Серверы одного приоритета перемешиваются для каждого запроса. Web-форма создаёт записи с priority `100`; другие значения можно задать через SQLite:

```sql
UPDATE upstreams SET priority=10 WHERE addr='192.168.1.53:53';
UPDATE upstreams SET priority=100 WHERE addr='1.1.1.1:53';
```

После офлайн-изменения базы перезапустите сервис. Если база изменена при работающем демоне, нажмите **Reload config**.

### Circuit breaker

После двух последовательных сетевых или retryable DNS-ошибок circuit открывается. Начальная пауза — 30 секунд, затем она увеличивается максимум до пяти минут. Успешный half-open probe закрывает circuit.

`SERVFAIL` и `REFUSED` считаются retryable DNS-ошибками и приводят к попытке следующего upstream. Если все реально опрошенные серверы вернули только такие коды, клиенту может быть возвращён последний из этих ответов.

## Условная пересылка DNS

Зоны хранятся в `forward_zones`, их серверы — в `forward_zone_upstreams`.

Значения `*.ru`, `.ru` и `ru` нормализуются до `ru`. Такая зона совпадает и с apex, и с поддоменами:

```text
ru
example.ru
www.example.ru
```

При нескольких совпадениях выигрывает самый длинный доменный суффикс. Совпавшая зона не переходит к default upstream, если все её собственные серверы недоступны.

Пример:

```text
*.ru  -> 77.88.8.8:53
*.lan -> 127.0.0.1:5353
default -> 1.1.1.1:853
```

Для зон действуют те же протоколы и priority, что и для основных upstream.

## Локальные DNS-записи

Постоянные записи находятся в `dns_records`:

```sql
CREATE TABLE dns_records (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  name TEXT NOT NULL,
  type TEXT NOT NULL,
  value TEXT NOT NULL,
  ttl INTEGER NOT NULL DEFAULT 0,
  enabled INTEGER NOT NULL DEFAULT 1
);
```

Поддерживаются `A` и `AAAA`.

- Пустое `value` означает authoritative `NOERROR` без адресов: NODATA.
- Несколько строк одного имени и типа дают multi-value ответ.
- `ttl=0` означает использование `local_record_ttl`.
- Обычное имя совпадает только само с собой.
- `*.example.com` совпадает с поддоменами, но не с `example.com`.
- Локальный ответ не пересылается upstream.

Локальные записи также могут запускать маршрутизацию, если их имя входит в специальные домены.

## Специальные домены и выбор маршрута

Шаблоны находятся в `special_domains` и могут дополняться внешними источниками.

Семантика:

| Шаблон | Совпадения |
|---|---|
| `example.com` | сам `example.com` и все поддомены |
| `*.example.com` | только поддомены, без apex |

Маршрут обрабатывается только если:

1. запрос содержит ровно один question;
2. имя совпало со специальным доменом;
3. тип запроса — A или AAAA;
4. включён соответствующий `route_ipv4` либо `route_ipv6`;
5. в ответе есть адреса этого семейства.

CNAME сам по себе не маршрутизируется, но A/AAAA-записи из той же секции Answer будут собраны.

### Выбор префикса

При `lookup_cidr=1` запрашиваются:

- `origin.asn.cymru.com` для IPv4;
- `origin6.asn.cymru.com` для IPv6.

Используется корректный покрывающий префикс. Ответы `/32` и `/128` не считаются полезной агрегацией, поэтому остаётся обычный host-prefix fallback. Любая ошибка запроса или разбора также приводит к `/32` или `/128`.

Team Cymru всегда запрашивается через default upstream policy, а не через условную зону.

### Порядок ответа и маршрута

При `reply_before_route=0`:

- dns-route ждёт маршрут;
- при ошибке маршрутизации возвращает `SERVFAIL` вместо DNS-ответа.

При `reply_before_route=1`:

- DNS-ответ отправляется сразу;
- создание маршрута ставится в очередь;
- если действительно появился новый kernel-маршрут, conntrack-записи с этим адресом удаляются, чтобы соединение, начавшееся раньше маршрута, могло повториться по новому пути.

## DNS-кэш

Кэшируются положительные ответы с ненулевым минимальным TTL. Negative и empty-answer ответы не кэшируются.

Ключ включает:

- выбранную forwarding policy и набор upstream;
- нормализованный полный DNS-запрос без transaction ID;
- тип и класс вопроса;
- флаги и EDNS-данные запроса.

TTL в Answer, Authority и Additional уменьшается на время нахождения в кэше. Поле TTL псевдозаписей OPT/TKEY/TSIG не меняется.

## Команды reload

| Команда | Поведение |
|---|---|
| **Reload config** / `POST /reload` | Перечитывает SQLite и использует уже активные snapshot внешних источников. Не читает файлы и не делает HTTP-запросы источников. |
| **Reload routes** / `POST /routes/reload` | Перезагружает route backend'ы и очищает route cache. В `kernel+bgp` зеркалирует выбранную kernel-таблицу в BGP. |
| **Reload sources** / `POST /record/sources/refresh` | Загружает оба класса источников, разбирает все файлы и активирует новые snapshot только при полном успехе. |

Обычные изменения через web-панель активируются сразу и не требуют отдельного **Reload config**.

## Runtime и мониторинг

Полезные endpoints:

```text
/                  текущее состояние
/statistics        счётчики и upstream circuits
/metrics           метрики Prometheus
/routes/errors     последние ошибки kernel-маршрутов в JSON
```

Основные группы метрик:

- DNS-запросы, cache hit/miss, локальные ответы, forwarding и SERVFAIL;
- добавление маршрутов, ошибки, queue drops, lookup и conntrack reset;
- состояния listener'ов и повторные bind;
- режим маршрутизации и BGP;
- состояние circuit и результаты запросов по каждому upstream;
- выбор и результаты каждой forwarding policy.

## Безопасность

- Admin HTTP не имеет встроенной аутентификации, авторизации, CSRF-защиты и HTTPS. Используйте loopback либо внешнюю защиту.
- HTTP-источники способны менять маршрутизацию и локальные DNS-ответы. Предпочитайте HTTPS или доверенные локальные файлы, ограничивайте права и доступ к настройке URL.
- DoT и DoH проверяют сертификаты. Отдельной настройки custom CA или insecure-skip-verify сейчас нет.
- Прямое изменение SQLite обходит валидацию web-формы до момента загрузки конфигурации.
